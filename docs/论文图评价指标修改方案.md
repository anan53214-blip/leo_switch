- 固定用户与多用户绘图统一从 `scripts/paper_metrics.py` 读取指标定义；

## 1. 方案结论

本次修改不改变现有实验的两层组织框架：

1. 固定用户数量对比：继续由 `scripts/compare_system_baselines.py` 在每个 `uXX` 目录生成算法对比图。
2. 多用户数量对比：继续由 `scripts/run_multiuser_scaling_suite.py` 在实验根目录汇总不同用户数量的扩展性曲线。

保留所有学习算法的平均回合 Reward 收敛曲线，但将单次训练曲线升级为“多个随机种子的均值曲线 + 95% 置信区间”。正文评价指标收敛为以下三组：

- 任务性能：任务成功率、成功任务平均时延、成功任务 P95 时延、截止期违反率。
- 切换与服务可靠性：服务连续率、切换失败率、阻塞时间占比、单位用户时间切换次数。
- 资源效率：单位成功任务能耗、MEC 负载 Jain 公平指数。

不建议继续把总能耗、任务完成率、任务结算率、雷达图归一化分数作为正文主指标。它们分别存在规模不可比、分母口径容易误解、信息重复或相对归一化容易夸大差异的问题。

这些文件名和固定用户/多用户两层目录结构继续保留，减少对现有实验流程的影响。

### 2.2 指标口径问题

1. `avg_delay` 当前由 `total_delay / resolved_tasks` 计算，成功任务、截止期违反任务和其他失败任务混在同一个平均值中。IEEE TMC 的代表性任务卸载论文使用的是“已完成任务的平均时延”，因此应新增独立的 `avg_success_delay`，不要静默修改旧字段含义。
2. 多用户图中的 `Average Energy` 实际读取 `total_energy`。用户数量增加时任务数也增加，总能耗天然上升，不能公平反映算法能效，应替换为 `energy_per_successful_task`。
3. `avg_load_balance_score`、`active_load_balance_score`、`mec_load_fairness` 和 `load_balance_coefficient` 存在兼容别名和覆盖关系。特别是 `normalize_load_balance_metrics()` 可能把方差系数重新写入 `mec_load_fairness`，导致同一字段在不同流程中含义不同。
4. `delay_energy_tradeoff.png` 读取的是 `energy_per_successful_task`，纵轴文字却仍为 `Energy per Resolved Task`，需要修正。
5. `task_completion_rate = completed_tasks / resolved_tasks` 会在大量任务仍未结算时产生偏乐观结果；正文应统一使用 `task_success_rate = completed_tasks / total_tasks`。
6. 当前雷达图按本次参与比较的算法做最小—最大归一化。增加或删除一个基线就可能改变所有算法的雷达形状，因此不适合作为核心结论图。
7. 当前多用户实验只有一个训练随机种子 `42`，每种方法只评估 3 个回合；图中只有点估计，没有跨训练种子的统计不确定性。

### 2.3 当前结果不能直接作为新版论文结果

`results/baseline_compare/multiuser_scaling_multiuser_6_7` 的汇总清单显示：

- 训练随机种子只有 `42`；
- 每种方法比较回合数为 `3`；
- 历史 `comparison_summary.csv` 仍包含旧 Reward 分量和已废弃的 MEC activity 字段；
- 历史结果没有记录当前要求的 `environment_schema_version = 5`；
- 历史结果生成于切换事务语义和 Reward v5 生效之前。

因此脚本修改完成后，应使用当前环境重新训练和评估，不能把旧结果与新结果混画。

## 4. 建议采用的指标定义

### 4.1 任务性能

#### 任务成功率

```text
task_success_rate = successful_tasks / total_tasks
```

成功任务指在截止期内完成计算的任务。该指标继续作为最重要的任务可靠性指标。

#### 成功任务平均时延

```text
avg_success_delay = mean(delay_i for i in successful_tasks)
```

当前 `avg_delay` 保留用于兼容历史日志，但不再作为论文主指标。新增字段避免修改旧字段语义。

#### 成功任务 P95 时延

```text
p95_success_delay = percentile(successful_task_delays, 95)
```

平均时延不能反映尾部体验。P95 只需要记录每个成功任务的最终时延，改动较小，适合作为一个有说服力的新指标。

#### 截止期违反率

```text
deadline_violation_rate = deadline_violations / total_tasks
```

它和任务成功率并不完全重复，因为任务还可能因其他原因失败或在回合结束时仍处于等待状态。

### 4.2 切换和服务可靠性

#### 服务连续率

```text
service_continuity_rate
    = 1 - service_interruption_seconds / total_user_seconds
```

该指标继续使用当前 schema v5 的时间口径，同时计入阻塞时间和切换中断时间。

#### 阻塞时间占比

```text
blocked_time_ratio = blocked_user_seconds / total_user_seconds
```

该指标与文献中的 user blocking rate 目标一致，但本系统采用的是“用户时间加权”的阻塞定义，不应在图中简单标为 `Blocking Rate`。建议统一标为 `Blocked User-Time Ratio`。

#### 切换失败率

```text
handover_failure_rate = failed_handovers / handover_attempts
```

切换失败必须按照当前事务语义统计：无线切换失败或任务迁移/入队失败均属于未提交的切换。

#### 单位用户时间切换次数

```text
handovers_per_user_minute
    = 60 * handover_committed / total_user_seconds
```

现有 `handover_frequency` 的单位是“次/用户秒”，数值过小且不直观。底层字段可保留，绘图时换算为“次/用户分钟”。

### 4.3 资源效率

#### 单位成功任务能耗

```text
energy_per_successful_task = total_energy / successful_tasks
```

固定用户和多用户图均使用这一口径，不再用 `total_energy` 比较算法能效。

#### MEC 负载 Jain 公平指数

对当前时刻所有可用 MEC 节点的归一化负载 \(x_i\) 计算：

```text
jain_mec_load_fairness
    = (sum(x_i))^2 / (M * sum(x_i^2))
```

仅在系统总负载大于零时采样，然后对一个回合内的样本求平均。空闲但可用的 MEC 节点必须参与计算，否则“只有一个节点承担全部工作”也可能得到接近 1 的虚高公平性。

新增 `jain_mec_load_fairness` 字段，旧的 `mec_load_fairness` 和几个别名仅用于读取历史结果，不再互相覆盖。

## 7. 统计协议

论文结果建议使用以下统一设置：

- 学习算法：至少 5 个独立训练种子；
- 每个训练种子：最终策略至少评估 10 个独立回合；
- 启发式算法：在与学习算法相同的 5 组环境种子上评估；
- 柱状图和扩展性曲线：先计算每个种子的评估均值，再对种子级均值计算 bootstrap 95% 置信区间；
- Reward 曲线：对相同训练步数处的种子曲线求均值和 bootstrap 95% 置信区间；
- 评估回合只用于降低单个种子评价噪声，不能当作独立训练种子；
- 固定 bootstrap 随机种子，保证论文图可复现。

为保持方案简单，正文先使用“均值 + 95% 置信区间”。NeurIPS 论文建议的 IQM、性能剖面和胜出概率可在算法数量和测试场景进一步扩大后作为附录统计，不要求第一阶段立即加入。

3. 阻塞时间占比与服务可用率互为补数；
4. 单位成功任务能耗分母正确；
5. 只有一个 MEC 节点承担工作时，Jain 公平指数不会被错误算成 1；
6. 多种子聚合均值和置信区间正确；
7. Reward 曲线按训练步数正确对齐；
8. 旧 schema 或缺少关键字段的结果不能进入新版论文图；
9. 固定用户和多用户脚本读取同一份指标定义。

## 9. 建议暂不加入的指标

### 吞吐量和用户满意度

部分 LEO 切换论文会报告用户速率、吞吐量或满意度，但当前系统没有完整的业务吞吐量和数据率需求模型。此时新增吞吐量图会把已有时延/链路模型包装成另一个缺乏独立含义的指标，不建议加入。

### 切换协议时延分布

IEEE INFOCOM 2024 将切换时延作为核心指标，是因为论文实现了实际 5G 核心网和接入网切换流程。当前系统的切换中断主要由配置参数决定。如果各算法面对相同固定切换时延，比较 P95 切换时延没有区分度。现阶段应报告服务连续率和切换频率；只有后续加入动态信令、链路和迁移时延模型后，再增加切换时延分布。

### 单一加权综合分数

Reward 已经承担训练目标的综合表达。评价阶段再把时延、能耗、成功率和连续率加权成一个总分，会掩盖算法具体的性能权衡，不建议作为论文主指标。

## 10. 推荐实施顺序

1. 先统一 `paper_metrics.py` 的字段定义和统计函数；
2. 增加成功任务时延样本及五个派生指标；
3. 修改固定用户绘图；
4. 修改多用户聚合和多种子目录；
5. 补充测试并做小规模两用户、两种子冒烟实验；
6. 最后重跑 `20/25/30/35/40` 用户的正式多种子实验。

完成后应达到以下验收标准：

- 固定用户和多用户图使用同一指标名称、公式和单位；
- 所有学习算法都有平均回合 Reward 收敛曲线；
- 正文图中的最终指标都有跨训练种子的 95% 置信区间；
- 不再用总能耗比较不同用户数量；
- 不再混用任务成功率、任务完成率和任务结算率；
- 不再混用不同含义的负载公平性字段；
- 旧 schema 结果不能被新版脚本静默读取。
